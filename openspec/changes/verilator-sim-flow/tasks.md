## 3. Green light

- [ ] 3.1 **[eda] [long]** End-to-end: build the model, run `sw/tests/helloworld.spm.elf` with `BOOTMODE=0 PRELMODE=0`. Verify (spec green-light scenario): "Hello World!" appears on stdout and the process exits 0.
      **Blocked — root cause not yet found.** Substantial real progress: `helloworld.spm.elf` builds via `make ig-sw-all` (needed the same host-side-checkout workaround as 1.1: this environment's Docker/virtiofs bind mount corrupts `bender`'s local-clone-via-hardlink step on *any* in-container `bender script`/`checkout` invocation - reproducible, not something `verilator.mk`'s own design causes, and not expected on a native Linux CI runner; worked around per-run by running `bender checkout` + the relevant `git submodule update` on the host immediately before the container step, never interleaving another container-side bender call). The full JTAG-DTM+DM sequence (IDCODE, `dmactive`, SBCS setup, LLC-SPM-config poll, ELF preload, `Command`-register `dpc` write, resume) runs to completion with the DMI protocol reporting success (`resp=0`) throughout - a real, working JTAG-DTM driver built from scratch against real RTL, confirmed via an isolated IDCODE readback (`0x00001071`, correct mandatory LSB=1) that basic TAP/shift mechanics are sound.
      What's actually blocked: `DMSTATUS` (and separately, SBA memory reads) return a value that never changes across repeated reads with generous idle time between them (confirmed via an isolated experiment: 8 `DMSTATUS` reads spaced 8000ns apart, *without* ever issuing a halt request, all returned the identical `0x00000011` - `allhalted`/`allrunning` both read 0, which is itself suspicious for a hart that should be running boot ROM). This means `HaltAndLoad()`'s "did the hart actually halt" check (now hard-erroring per the fix above, rather than silently continuing as it originally did) would legitimately fail if run to completion - the run that produced the FAILED/exit-code-3 result described below predates that fix. Ruled out: TAP-level bit ordering/navigation (IDCODE proves it sound), the halt request specifically as a trigger (the no-halt experiment shows the same stuck pattern), and the `DmiRead` issue-then-retrieve idle-gap (added, did not change the outcome).
      **Also tried:** read `pulp-platform/croc`'s `riscv_dbg_simple` reference driver (same `riscv-dbg` IP lineage) at the user's suggestion; it exposed a real gap - `dm_pkg.sv`'s DMI error/busy latch is sticky and needs an explicit `dtmcs.dmireset` (a separate IR, `0x10`) before retrying a busy DMI transaction, which this driver never did. Implemented (IR tracking + `WriteDtmcs`/`ResetDmi`, called before every busy-retry) - a real, worth-keeping protocol fix, but it did not change the observed symptom: this driver's traces never actually showed `resp=BUSY` (always `resp=0` with frozen data), so the retry-then-reset path was never exercised. Also read the canonical (unpatched) `jtag_test::riscv_dbg` driver `vip_cheshire_soc.sv` itself uses (`riscv-dbg`'s `tb/jtag_dmi/jtag_test.sv`) - confirmed this driver's MSB-first send convention and same-address NOP-retrieve trick both already match it exactly; no new divergence found there either.
      **Decision (2026-09-01): deferred, not abandoned.** A licensed-simulator cross-check (Questa on a Linux VM, or standing up an Xcelium lane - evaluated, would need `bender script flist-plus` + a hand-ported do-file since Bender has no native `xcelium` target) remains the most likely way to actually root-cause this, but it is not worth blocking further infra work on securing a license/VM for. Root cause stays open; picking this back up is follow-up work, not a gate on Phase 3. See design.md's addendum for the still-available low-cost angle (an isolated FST/VCD trace, no licensed simulator needed) if anyone revisits this before a licensed cross-check is available.
