Notes
-----
The VM Modify is now exactly the intended change: `identity` is the
SystemAssigned identity being added. storageAccountType is explicitly NoEffect.
securityProfile, diskSizeGB and customData no longer appear - all three are
behind parameters that omit them when adopting.

Every leaf the template sets on the VM was diffed against the live GET before
this preview: 0 mismatches, and nothing sent that is absent on live. That check,
not the preview, is what catches PropertyChangeNotAllowed.

Two Modify entries are what-if artifacts no deployment can settle:
  - NIC `kind` and `allowPort25Out` are read-only and ARM-computed; Bicep
    rejects declaring them (BCP187 / BCP037).
  - The blob role assignment's `principalId` comes from a runtime reference()
    what-if cannot resolve; the stored value already equals the identity's
    principalId (6e5681a6-e861-476f-a091-72d01bb57531), verified directly.
Both fall under the read-only-property exemption in the azure-infrastructure
spec's idempotence requirement.

The Key Vault Secrets User assignment is absent because it lives in a nested
module whose principalId comes from the VM identity that does not exist yet.
Task 2.3 verifies it after deployment.
